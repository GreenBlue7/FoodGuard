# 비동기 검수 처리

## 사용자 흐름

`POST /api/inspections`는 입력/제품 상태를 검사하고 접수 당시 제품 정보와 광고를
DB에 저장한 후 기존 형식 `{ "jobId": "..." }`와 HTTP 200을 반환한다.
200은 접수 성공이며 판정 완료를 뜻하지 않는다. 잘못된 입력은 기존처럼 400/409다.
재검수, 현재 광고 재검수, 선택한 수정안 검증도 같은 흐름을 사용한다.

기존 `GET /api/inspections/{jobId}`로 PENDING → RUNNING → DONE/FAILED/TIMEOUT을
조회한다. 원문/제품 정보는 접수 시점의 스냅샷이며, 대기·진행 상태도 이력에 남는다.
완료 전에는 layer2가 null이고 리포트·추천 조회는 409다. 재검수 비교의 bothCompleted는
완료 전 false이며, 수정안 검사 상태도 PENDING이다. 진행 중인 기록으로 재검수할 수 없다.
접수 createdAt은 유지하고 처리 종료 시 completedAt을 추가한다.

## 저장과 실행

`011_inspection_job_queue.sql`을 시작 전에 적용한다. 검사 기록과 대기열 입력은
동일 트랜잭션으로 저장한다. 메모리에만 작업을 넣지 않는다.
작업 번호와 소유자는 기존 inspection_records를 사용하며 사용자별 조회 통제를 유지한다.

별도 스케줄러가 기본 1초마다 한 작업을 처리한다. 기본 작업자 동시성은 1이다.
식약처/이메일 작업은 별도 maintenance 스케줄러에서 실행해 AI 응답 대기가 막지 않는다.
FOR UPDATE SKIP LOCKED로 작업을 선점하며 선점 토큰으로 늦은 결과 덮어쓰기를 막는다.
외부 judge 호출을 하는 동안 작업 선점/완료 DB 트랜잭션은 열어두지 않는다.
대기 중 제품 version이 바뀌면 유료 호출 없이 FAILED(PRODUCT_CHANGED)가 된다.
호출 도중 변경돼도 결과를 DONE으로 저장하지 않으며 최신 기준으로 재검수가 필요하다.

## 중단·복구와 비용

아직 선점되지 않은 PENDING은 서버 재시작 후 이어서 처리한다.
AI 호출 중 중단된 RUNNING은 기본 10분의 선점 유효기간 이후 FAILED로 바뀐다.
유효기간은 연결+응답 제한 두 번과 1분 여유보다 짧아지지 않는다.
복구 코드 WORKER_INTERRUPTED를 저장하며 **자동으로 AI를 다시 호출하지 않는다**.
과금 여부를 알 수 없어 사용자가 새 검사를 명시적으로 요청하도록 한다.
이는 정확히 1회 AI 과금 보장이 아니라, 불확실한 작업의 자동 재호출을 피하는 정책이다.
DB에 결과를 기록하지 못한 경우에도 같은 작업을 자동 재호출하지 않는다.
FAILED/TIMEOUT을 자동 반복하지 않으며, 완료 후 대기열 행과 중복 입력은 삭제한다.

브라우저의 기존 3분 조회 제한은 전체 대기열 대기 시간보다 짧을 수 있다.
화면에서 기다리기를 중단해도 접수한 검사는 취소되지 않으며, 이력에서 다시 조회한다.
진행 중인 동일 요청의 중복 접수는 아래 정책으로 억제한다. 서로 다른 요청의 호출량·사용자별 대기 제한은 후속 작업이다.

## 설정·검증

- INSPECTION_JOBS_WORKER_ENABLED: 기본 true. 점검 시 false로 접수만 받고 실행을 멈출 수 있다.
- INSPECTION_JOBS_POLL_MS: 기본 1000.
- INSPECTION_JOBS_LEASE_MS: 기본 600000. 실제 최소값은 judge 연결/응답 제한을 반영한다.
- 단위/HTTP 테스트는 worker-enabled=false로 두고 worker를 명시적으로 실행한다.
- 실제 PostgreSQL에서 접수 응답 전 judge 미호출, RUNNING 조회, 동시 중복 선점 방지,
  대기 복구, 만료 처리, 늦은 완료 거부, 실패/시간초과, 제품 version 변경을 검증한다.
- 알림 → 현재 광고 → 수정안 검증 및 문장 비교 테스트도 비동기 처리 후 결과를 확인한다.

실제 Gemini 판정의 품질·시간·비용 검증은 사용 가능한 키가 있을 때 별도로 수행한다.

## 진행 중인 동일 요청 재사용

012 SQL은 inspection_records에 request_fingerprint와 활성 작업의 사용자별 UNIQUE
인덱스를 추가한다. 접수 트랜잭션은 사용자 행을 잠근 뒤 동일한 PENDING/RUNNING이
있으면 그 작업 번호를 반환하며 새 검사 기록이나 대기열을 만들지 않는다.
서로 다른 서버 인스턴스에도 같은 DB 잠금과 제약이 적용된다.

SHA-256 식별값에는 정규화된 요청, 제품 스냅샷/버전, 실제 judge 제품 입력,
재검수 원본 번호, 수동 문장 연결, 선택한 수정안을 포함한다.
요청마다 생성한 UUID, 접수 시각, JSON 객체 키 순서는 제외한다.
다른 사용자, 다른 광고, 다른 제품/버전, 다른 원본/수정안/문장 연결은 합치지 않는다.
광고 내부 공백/줄바꿈은 위치 정보에 영향을 주므로 임의로 변경하지 않는다.

DONE/FAILED/TIMEOUT 및 중단 복구 후에는 같은 입력도 새로운 작업으로 접수한다.
완료된 결과 캐시나 시간별 호출 제한은 아니다. 여러 종류의 요청을 과도하게 접수하는
것은 별도 제한이 필요하다. 응답 형태/상태 코드는 기존 jobId 및 HTTP 200을 유지한다.

012 적용 전의 대기·진행 작업도 다음 접수 시 저장 입력으로 식별값을 복원한다.
이미 존재하던 중복 작업은 취소하거나 자동 재호출하지 않고 기존 작업을 우선 재사용한다.
완료 기록은 이 과정에서 다시 쓰지 않는다.
