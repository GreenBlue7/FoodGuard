# 여러 검사 한 번에 접수

제품 하나와 광고 문구 하나로 구성한 검사 항목을 1~3건 묶어 접수한다. 항목마다 독립적인 jobId를 반환하고 기존 DB 대기열에서 차례로 처리한다. 여러 제품의 기능성을 합쳐 판정하지 않는다. judge API와 판정 코드는 변경하지 않았다.

## API

인증 필요: `POST /api/inspections/batch`

```json
{
  "items": [
    { "productIds": ["제품-A-신고번호"], "adText": "상품 A의 광고 문구" },
    { "productIds": ["제품-B-신고번호"], "adText": "상품 B의 광고 문구" },
    { "productIds": [], "productTypeAnswer": "GENERAL", "adText": "미등록 일반식품의 광고 문구" }
  ]
}
```

HTTP 200은 목록 전체 접수 성공이다. 완료를 뜻하지 않는다. items는 입력 순서를 유지하며 index는 0부터 시작한다. 번호는 전역 검사 번호이고 연속 번호를 보장하지 않는다.

```json
{
  "items": [
    { "index": 0, "jobId": "101" },
    { "index": 1, "jobId": "102" },
    { "index": 2, "jobId": "103" }
  ]
}
```

각 항목은 기존 `GET /api/inspections/{jobId}`로 상태·결과를 조회한다. 본인 기록만 조회할 수 있다. PENDING → RUNNING → DONE/FAILED/TIMEOUT이며 한 작업의 실패·시간 초과가 다음 작업을 취소하지 않는다. 사용자가 화면을 닫아도 접수된 작업은 DB에 남는다. 전체 검수 이력·리포트·재검수에도 기존처럼 개별 기록으로 연결한다.

## 입력·한도·중복

- 항목별 최대 제품 1개, 공백·줄바꿈 포함 광고 3,000 Unicode 코드포인트, 제품 정보 준비 조건 등 INPUT_VALIDATION.md의 검증을 그대로 적용한다.
- 목록 누락/null/빈 목록/4건 이상은 400 INVALID_BATCH_SIZE다. null 항목·잘못된 JSON·문구·제품 입력은 기존 입력 오류 형식을 사용한다. 항목 입력 오류는 message에 1부터 시작하는 항목 번호를 표시한다.
- 사용자별 기존 대기·진행 최대 3건, 최근 60초 새 접수 최대 5건 제한을 공유한다. 초과 시 기존 429/Retry-After 계약을 유지한다. 한도를 우회하거나 묶음 하나를 한 건으로 계산하지 않는다.
- **전체가 한 트랜잭션이다.** 중간 항목의 400/409/429나 저장 오류 시 새 기록·대기열·접수 카운터를 전부 롤백한다. 기존 작업은 그대로 유지한다. 롤백 중 사용한 DB 번호에 빈 번호가 생길 수 있다.
- 동일한 PENDING/RUNNING 요청은 기존 jobId를 재사용하고 추가 한도를 쓰지 않는다. 목록 안의 중복 항목도 같은 번호표를 받을 수 있다. 완료·실패 후의 재요청은 새 검사이며 유료 호출이 발생할 수 있다.
- 접수 트랜잭션에서는 AI를 호출하지 않는다. 기존 worker가 커밋된 항목을 처리한다. 현재 실행 동시성은 기존 단일 worker 설정을 유지한다.
- 네트워크 오류로 응답이 유실되면 이미 접수됐을 수 있다. 자동으로 재접수하지 않고 검수 이력에서 먼저 확인한다. 완료 결과 캐시나 무기한 멱등 접수를 제공하는 API는 아니다.

## 화면

검사 작성 화면에서 상품과 문구를 입력하고 ‘검사 목록에 담기’를 누른다. 다음 상품을 검색하고 다른 문구를 입력해 목록에 추가할 수 있다. 목록은 최대 3건이며 삭제 후 다시 작성할 수 있다. 현재 작성 중인 항목은 목록에 담아야 함께 접수된다. 기존 한 건 바로 검사도 유지한다.

목록 접수 후 `/inspection-batches?jobs=101,102,103` 화면에서 번호표별 제품명·광고 미리보기·상태·상세/결과 링크를 표시한다. URL의 jobId는 조회용이며 각 요청의 소유권은 서버에서 다시 확인한다. 새로고침해도 해당 번호표를 다시 조회한다. 각 번호표는 최대 3분간 폴링하고, 시간 경과·조회 오류 시 새 접수 없이 ‘상태 다시 조회’를 제공한다. 이력에서도 다시 확인할 수 있다.

접수 전 작성 목록은 메모리에만 보관하며 새로고침 시 사라진다. 로그아웃/세션 종료 시 작성 상태를 비운다. 접수 후에는 기존 DB 기록으로 보관하므로 새 SQL이나 별도 묶음 DB 테이블은 추가하지 않았다.

## 검증

- PostgreSQL 기반 backend 전체 200 tests / failures 0 / errors 0. 새 HTTP 테스트 9개 포함.
- 제품별 입력 분리, 순차 처리·실패 후 다음 작업, 잘못된 입력·제품 준비 실패·활성/시간 한도 초과의 전체 롤백, 중복·동시 목록 접수, 로그인·소유권을 검증했다.
- 프런트 oxlint/ESLint/vue-tsc/production build 통과.
- 별도 DB와 local-stub-no-ai 서버로 상품 A/B/C를 목록에 담고 번호표 3개 접수, 검사 중/대기 상태, 완료 및 결과 링크, 새로고침을 확인했다. AI 서버 호출은 항목별 총 3회였다. 실제 Gemini 호출과 품질·비용 검증은 포함하지 않는다.
